My [chat assistant](/assistent) could talk, and that was all it could do. Two things I wanted from it:

- **Talk to [Bundestakt](https://www.bundestakt.de)**, a free API with summaries of Bundestag plenary sessions and fact-checks of what was claimed in the debates. Asking what happened in the session on 9 September should get an answer from the actual record, not from whatever the model half-remembers.
- **Make an image without leaving the chat.** The image generator already had its own page. Describing a picture mid-conversation and then being sent somewhere else to get it is a silly way to run a website.

Both are the same problem: the model has to reach something outside itself, in the middle of writing an answer.

What I was unsure about was where that reaching happens. I had only ever met tool calling from inside LangChain and LangGraph, in Python. There a tool call and a model call look like the same kind of thing — nodes in one graph, running in one process — and I had quietly assumed they have to be.

This site has no process to put them in. It is built once, ahead of time, into plain files with [Vike](https://vike.dev): when you visit, no program of mine is running anywhere. Next to those files sit a handful of serverless functions — small pieces of code that wake up when something calls them and shut down again afterwards. One of them is the paid endpoint that talks to Mistral for me, and it will not help either: it passes my list of tools along to the model and hands the model's reply straight back, without ever running anything itself.

So the loop runs in the browser. Which, it turns out, is not a workaround at all. This is one of the quietly amazing things about the modern web: a site built to static files is still a fully functional application. It can fetch from anywhere, keep state, wait for a human to click something, and run a loop for as long as it likes. The one thing it genuinely cannot do is keep a secret — and that, as far as I can tell, is the only reason any of this ever needs a server.

## One turn, payload by payload

I wanted to ask my model _"What did the Bundestag debate on 9 September?"_ and have the answer come from Bundestakt. Here is the whole turn, and the rest of the post walks through it step by step.

### 1. Send the usual request, plus `tools`

When you chat with a model, you send it a list of messages — who said what, in order. Tool calling adds a second list next to that one. Think of it as a menu: here are the things I can do for you, here is what each one is good for, and here is what you would have to fill in to order it.

The model cannot cook anything on that menu. It can only read it and tell me what it would like. Which means the `description` field is doing more work than it looks like it is doing: it is the only thing the model ever learns about a tool. Not my code, not Bundestakt's documentation — just that sentence. So rules about _how_ to use the thing get written there, in plain language, for a reader: "call without a slug first to find the session, then call again with its slug for the detail."

```bash
curl https://llm-agent.fretchen.eu -d '{
  "messages": [
    { "role": "user", "content": "What did the Bundestag debate on 9 September 2026?" }
  ],
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_sitzungen",
      "description": "List Bundestag plenary sessions (Bundestakt), or fetch one session's full detail by slug. Call without a slug first to find the right session, then call again with its slug for details.",
      "parameters": { /* slug, plus von / bis as ISO dates to narrow the range */ }
    }
  }]
}'
```

(A real call also carries an `X-PAYMENT` header, because this endpoint charges a fraction of a cent per message. That is [a different story](/blog/32/) and changes nothing here.)

### 2. The model asks

What comes back is the model's answer — it is just not made of words.

Replies always arrive in the same box: a `choices` list, with a `message` inside it. Normally that message has `content`, the text you would read on screen. This time `content` is empty and a `tool_calls` list has taken its place. And `finish_reason`, the label saying why the model stopped talking, says `"tool_calls"` instead of the usual `"stop"`.

Nothing has run at this point. Nothing has been fetched. The model does not even know whether `get_sitzungen` works. It has read the menu and placed an order, and it has attached an `id` to that order like a ticket number, so the answer can later be handed back against the right request.

```json
{
  "choices": [
    {
      "finish_reason": "tool_calls",
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_a1b2c3d4",
            "type": "function",
            "function": {
              "name": "get_sitzungen",
              "arguments": "{\"von\": \"2026-09-09\", \"bis\": \"2026-09-09\"}"
            }
          }
        ]
      }
    }
  ]
}
```

One thing here regularly trips people up: `arguments` is not an object, it is a string. The model wrote data out as text, and that text has to be unpacked before it is of any use — and it can arrive broken. Mine unpacks it inside a `try` that falls back to an empty object, because a model that garbles its own order should not take the whole chat message down with it.

Worth saying plainly here, because everything below depends on it: **the model has no memory**. Every request is the first time it has ever seen this conversation. It is not sitting somewhere between my messages, holding the thread. The only reason it appears to remember anything is that I send the entire conversation again, from the beginning, every single time.

### 3. My code runs it

This is the part that surprised me, and it is where the static site stops feeling like a limitation.

The page just calls Bundestakt itself. An ordinary `fetch`, the same one any React component makes to load anything — from your browser, straight to `bundestakt.de`, with nothing of mine in between. Browsers normally refuse to let a page read another site's data unless that site explicitly says it is fine; Bundestakt says it is fine, and asks for no key, so there is nothing in the way. A tool that needed a password would be the one case that has to detour through a serverless function, because the browser is the one place a secret cannot live.

The code comes in two halves. One fetches and can fail; the other is a **pure function** — same input, same output, no surprises, which is why it is the easy half to test. Its job is to throw almost everything away:

```typescript
// tools/bundestakt.ts — no React in here, just a fetch and a pure projection.
export async function fetchSitzungen(): Promise<unknown> {
  const res = await fetch("https://www.bundestakt.de/api/v1/sitzungen");
  if (!res.ok) throw new Error(`Bundestakt request failed: HTTP ${res.status}`);
  return res.json();
}

export function selectSitzungen(raw: unknown, args: { slug?: string; von?: string; bis?: string }) {
  const sitzungen = (raw as RawSitzungenResponse | null)?.sitzungen ?? [];

  if (args.slug) {
    const found = sitzungen.find((s) => s.slug === args.slug);
    if (!found) return { status: "not_found" };
    const { protokollPdf, ...rest } = found;
    return { status: "ok", sitzung: rest };
  }

  const filtered = sitzungen.filter((s) => (!args.von || s.datum >= args.von) && (!args.bis || s.datum <= args.bis));
  return {
    status: "ok",
    sitzungen: filtered.map((s) => ({
      slug: s.slug,
      datum: s.datum,
      kernthema: s.kernthema,
      schlagzeilen: (s.in30Sekunden ?? []).map((p) => p.titel),
      url: s.url,
    })),
  };
}
```

That throwing-away is the whole point of the second half. Bundestakt's list is 74 KB across 21 sessions, most of it five-paragraph summaries of debates nobody asked about. Keeping only slug, date, topic and headlines brings it to 7.3 KB. Since the model has no memory, this result does not get read once — it goes into the conversation and is sent again, in full, with every later message of the same turn. A fat tool result is a bill you pay over and over.

### 4. Send the same array again, grown

Now the same list of messages goes back to the same endpoint, with two things added to the end: the model's own order, handed back word for word, and the answer to it, tagged with that ticket number. That answer is a third kind of message — not from the person, not from the model, but `role: "tool"`.

```json
{
  "messages": [
    { "role": "user", "content": "What did the Bundestag debate on 9 September 2026?" },
    {
      "role": "assistant",
      "content": null,
      "tool_calls": [{ "id": "call_a1b2c3d4", "type": "function", "function": { "name": "get_sitzungen", "arguments": "{\"von\": \"2026-09-09\", \"bis\": \"2026-09-09\"}" } }]
    },
    {
      "role": "tool",
      "tool_call_id": "call_a1b2c3d4",
      "content": "{\"status\":\"ok\",\"sitzungen\":[{\"slug\":\"21-92-2026-09-09\",\"datum\":\"2026-09-09\",\"kernthema\":\"Haushalt 2027 und der Schock von Sachsen-Anhalt\",\"schlagzeilen\":[\"Weidel greift an, Merz kontert\",\"140 Milliarden fuer Verteidigung\",\"Gekuerzt wird bei den Familien\"],\"url\":\"https://www.bundestakt.de/sitzung/21-92-2026-09-09\"}]}"
    }
  ],
  "tools": [ ... same as before ... ]
}
```

Same endpoint, same shape as step 1. This time the model writes prose, `finish_reason` comes back as `"stop"`, and the turn is over. If it had wanted the full record it would have ordered again, with `slug` this time, and the list would have grown by two more messages.

That is the bit I had wrong for a long time. There is no callback, no webhook, no connection held open, nothing registered with anyone. The entire link between Mistral and my React code is that **a list grows and gets sent again**, and the ticket number is the only thread tying an answer back to the request it answers.

Which means the loop is a `for` loop with a `break` in it. Two things to watch: the list being pushed to at the bottom, and the `break` that fires the moment the model finally writes words instead of ordering something.

```typescript
for (let hop = 0; hop < MAX_HOPS; hop++) {
  const offered = offeredTools.filter((t) => !failedTools.has(t.function.name));

  const data = await payAndSend(convo, {
    tools: offered.length > 0 ? offered : undefined,
  });

  const choice = data.choices?.[0];
  const toolCalls = choice?.message.tool_calls;

  if (choice?.finish_reason !== "tool_calls" || !toolCalls?.length) {
    finalContent = choice?.message.content ?? null;
    break;
  }

  convo.push(choice.message); // the assistant turn: content null, tool_calls intact

  for (const call of toolCalls) {
    const { result, recoverable } = await runToolCall(call);
    if (result.status !== "ok" && !recoverable) {
      failedTools.add(call.function.name);
    }
    convo.push({ role: "tool", tool_call_id: call.id, content: JSON.stringify(result) });
  }
}
```

That is [the real one](https://github.com/fretchen/fretchen.github.io/blob/main/website/utils/toolLoop.ts), minus its comments. One trip round that loop is a **hop** — one journey to the model and back, paid for separately from the last. `MAX_HOPS` is 4, because a model that never stops ordering would otherwise bill me in a circle. Four is not a principle; it is the smallest number that fits the longest flow I have, which is list → detail → answer with one hop spare.

Two things in there were bought with a bad afternoon. `failedTools` exists because image generation once kept failing and the model kept ordering it again — entirely reasonably, since nothing told it the failure was permanent. Three wallet prompts, three payments, no answer, because no hop ever got as far as writing a sentence. Now a tool that fails is simply off the menu for the rest of the turn. The exception is a failure that is really an answer — a mistyped session slug _should_ be retried with a corrected one — so a tool can mark its own result as worth another go.

And `offered.length > 0 ? offered : undefined` is there because an empty menu is not the same as no menu. Handing over `tools: []` still says "here is a list of what I can do", and it happens to be empty; leaving the word out entirely says nothing about tools at all. Once every tool has failed, the second one is what I mean, so the code drops the key rather than sending an empty list.

## Four tools, two shapes

There are four tools on offer now — `get_sitzungen`, `search_claims`, `get_analytics`, `generate_image` — and they come in two shapes.

**Read something and shrink it.** A fetch, then a pure function that cuts the response down to what an answer needs. Bundestakt and the site's own traffic figures. Boring in the good way.

**Ask the user first, then act.** `generate_image` spends seven cents of real money, so the model ordering it does not make it happen. The code puts a confirmation card on screen — the prompt, the size, the price — and then the loop simply stops at that line and waits, the way a half-finished function waits for whatever it asked for. It can wait indefinitely. Whatever the person decides — confirm, rewrite the prompt, cancel — comes back to the model as a status like `user_declined`, and the model writes the sentence explaining it.

A tool call is a request, not a commitment. Which makes the gap between the asking and the doing a natural place to put a human, and that gap costs nothing to open: the loop is already just code, sitting in a browser, on a page with a user in front of it.

The tool files themselves have no React in them. Partly taste, partly so that the fetch-and-shrink half of each one can be imported by something that is not this page.

## Is this an agent? Do I need MCP?

It picks whether to act, which tool to use, and what to fill in. It reads the result and decides what comes next. It chains: find the session, fetch its detail, then answer. By most working definitions that is an agent.

It also forgets everything the moment the turn ends. Those tool messages live in a list that exists only while one message is being answered, and then it is thrown away — so the model's own closing sentence is its entire memory of having generated an image. It follows no plan that my code owns. It stops after four hops. And the whole thing is about forty lines.

Which is the uncomfortable part. The vocabulary around this — agents, orchestration, MCP — sounds like it describes something considerably larger than what I wrote. MCP is worth a sentence in plain terms: it is an agreed format for describing tools and reaching them, so that a tool written by one person can plug into a chat program written by another, without the two ever having met. It does not change the exchange above at all. The model still orders, something else still runs it, the result still goes back as a `role: "tool"` message. For four tools I wrote myself, against one chat page I also wrote, it would have bought me nothing yet. That changes the first time I want somebody else's tool in here.

Where the real line sits, I am honestly not sure. The [growth agent](/blog/29/) on this same site is the other shape entirely: a scripted pipeline that runs on a timer, keeps its notes in a file store so it remembers things between runs, and leaves me a queue of drafts to approve by hand. It needs minutes, and it needs a memory. Between "forty lines in a browser" and that, I have a practical boundary — how many hops, how much money, how long, whether anything has to survive closing the tab — and not a conceptual one. Possibly there is no conceptual one, and that is why "agent" has stopped carrying much information.

## What it cost

One loop file, four small tool modules, and a confirmation card. The thing I would do differently is write the loop first: every decision that turned out to matter — how many hops, what happens when a tool fails, what a tool is allowed to hand back — lives in it, and I found all of them by getting them wrong there.

It runs on [the assistant page](/assistent) if you want to watch a list grow.
