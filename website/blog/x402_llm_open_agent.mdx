Ideally, I want to use a good AI model without the need of personal information. Just pay for the messages I actually send and tell nobody who I am.

A year ago I built [the first version](/blog/16/) of such an assistent. It was an experiment to see if this idea can be realized technically. The user chats with an LLM, pays fractions of a cent per message, and never gave me an email address, credit card or other personal information.
You prepaid into a smart contract, and then I settled messages in [batches](/blog/15/) to keep transaction costs small. However, this implementation had a number of rough edges:

- **I held the money.** Deposits sat in a contract I owned and could upgrade. Users had to trust that I would not walk off with them, and there was no particular reason they should.
- **Every message left a public trace.** Settling on-chain meant publishing, for each message, which address sent it, what it cost, and when. Balances were readable by anyone. I had built an assistant you could pay anonymously that kept a public log of everyone's usage. That bothered me more the longer it ran — enough that I never really used my own assistant.
- **It was custom-made.** The code was open source, but the API was artisanal. I was learning serverless functions at the time and wanted the simplest thing that worked. So there was no specification, and nothing another program could find or read.

None of these were bugs but real limitations that bothered me.

## Moving towards x402

One thing that allowed me to tackle of those now is the availability of new technology in form of x402 [batch-settlement](https://x402.org/x402-batch-settlement/). I already covered [x402 itself](/blog/22/) when I put it behind my image generator.
Briefly: you call an endpoint, get back `402 Payment Required` with machine-readable instructions, sign a payment, and retry. No accounts, no API keys.

That previous approach used the `exact` scheme — one signed payment, one on-chain settlement, per request. This works nicely for a 7-cent image. However, this approach is too expensive and slow for AI agents where a message typically costs a fraction of a cent. Gas costs would simply be too high.

The new _Batch-settlement_ uses a payment channel instead, which works like a bar tab:

1. **Open the tab.** Your first message deposits USDC into an escrow contract. This is your one transaction.
2. **Run up the tab.** Every later message signs a _voucher_ — an off-chain IOU capping what the agent may claim in total. Just a signature. No transaction, no gas, no waiting.
3. **Cash out.** A cron job on my side runs `claimAndSettle()` every 12 hours.

Each voucher supersedes the last, so only the final one is ever redeemed. A hundred messages produce a hundred signatures and one transaction.

And the escrow is the canonical `x402BatchSettlement` contract — the same address for everyone using the scheme. I did not have write it or maintain it, it comes with the x402 tech stack. And quite importantly money only moves in the end against a voucher the user signed, for an amount they capped.

Pricing got more honest as a side effect. Each message advertises a ceiling of at most 0.003 USDC, and the voucher signs against that ceiling. The actual claim is computed from real token usage afterwards, and it is almost always well under. You authorize an upper bound; I charge what it cost.

|                        | First version                         | Now                                                   |
| ---------------------- | ------------------------------------- | ----------------------------------------------------- |
| Who holds deposits     | My upgradeable contract               | Canonical escrow, nobody's to upgrade                 |
| Unit                   | ETH                                   | USDC                                                  |
| Per message, on-chain  | Address, token count, cost, timestamp | Nothing                                               |
| Getting your money out | Via my contract                       | You withdraw it yourself, even if I disappear         |
| Settlement trust       | My batch, my Merkle root              | Facilitator — swappable, and cryptographically capped |

There is still a facilitator in the picture, and I [complained about facilitator trust](/blog/22/) when I built one. What changed is that these facilitators are really interchangable, so pointing my agent at a different one is a configuration change.

## One API that everyone already uses

With payment handled by a standard, I also want to see if I might be able to move the LLM API to the OpenAI chat-completions format:

```json
{
  "model": "mistral-large-latest",
  "messages": [{ "role": "user", "content": "Explain payment channels" }]
}
```

So now you get back a standard `chat.completion` object, `choices` and `usage` and all. The OpenAI response is the de facto standard for LLMs so I gained hugely in compatibility. One limit remains: you cannot point a stock OpenAI SDK at this endpoint.
The SDK sends `Authorization: Bearer`, my endpoint wants a payment channel.

## Being findable on x402scan

The other really cool thing of these standardizations is that a machine gets enabled to find the agent. x402 sets a remarkably low bar for this, which is most of its appeal. My agent serves its own [OpenAPI document](https://llm-agent.fretchen.eu/openapi.json) at `/openapi.json`.
It is not documentation for humans; it is the API scheme. It declares the schemas, the model IDs actually served, the price ceiling, and — the part that makes it a category rather than a one-off — a service type and an interop floor:

```json
"x-service-type": "llm/v1",
"x-interop-floor": "A compatible llm/v1 agent MUST advertise at least one
  accepts[] entry with asset USDC on network Optimism (eip155:10) or
  Base (eip155:8453), scheme batch-settlement."
```

A very low bar: speak this body shape, accept USDC on Optimism or Base via batch-settlement, and you are an `llm/v1` agent. Anything that can pay one can pay all of them.

[x402scan](https://www.x402scan.com) is a crawler that indexes x402-payable endpoints. It found my agents, read their specs, and listed them — the [AI assistant](https://www.x402scan.com/server/f2788b7c-7933-42c2-9e69-ed57cf91e58a) and the [image generator](https://www.x402scan.com/server/1246cf89-3c1d-4a2d-9cb7-d96a4b40e9a6).
All I had to do was prove the origins were mine: sign the origin URL with the receiving wallet, paste the signature into `x-discovery.ownershipProofs`. A one-line script and a static field. A directory I have no relationship with can now hand my agent to a paying client that has never heard of me.

## Adapting the frontend

The updated frontend can now point at any `llm/v1` agent. The `useX402Chat` hook takes an agent URL, mine is just the default, and channel state is keyed per origin so switching is isolated. I built it, tested it, shipped it.
The assistant is at [/assistent](/assistent). Connect a wallet, deposit a little USDC on Optimism or Base, chat. The first message opens a channel; the rest are signatures.

For the machine side, [/agent-onboarding](/agent-onboarding) walks through the whole flow — the 402, the channel lifecycle, the discovery document — and checks a live endpoint against the `llm/v1` contract as you go.

## What it bought

All of these feels like a substantial step forward:

- Giving up custody shrank my [threat model](/blog/30/). The worst case for my owner key used to include draining everyone's deposits; now there are nobody's deposits to drain.
- Dropping per-message settlement improved privacy. The first version went for anonymous payment and still needed a fairly detailled usage log. This one publishes nothing per message.
- And adopting the standards did more for reuse than any API I would have written myself. Two of my services now sit in a directory I never registered with.

New standards keep appearing for things I built myself, and I will keep adopting them. It usually costs less than the migration looks like it will. If you try the assistant, I would like to hear how it went.
